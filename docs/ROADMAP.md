# FeldKit: план реализации

Документ для обсуждения. Код по нему ещё не написан. Для каждого пункта: что делаем, как, чем проверяем и когда считаем готовым.
В конце собраны вопросы, на которые нужен ваш ответ, и то, что я делать не буду.

## 0. Принципы работы (как делали BPM)

1. **Сначала эталон, потом код.** Для каждой функции ищем объективный способ проверки: утилита-оракул на этом Mac, ваши
   размеченные сэмплы, образы дисков, собранные macOS. Результат с цифрами точности идёт в README, без обещаний «на глаз».
2. **Данные из вашей библиотеки читаются, но не копируются в репозиторий.** Скрипты `tools/make-*.py` берут путь аргументом,
   пишут только в `app/build/fixtures` (в `.gitignore`).
3. **Чтение никогда не ломается из-за новых функций.** Всё новое включается с запасным путём назад (UAS → обычный USB,
   новый просмотрщик → «открыть в другом приложении»).
4. **Любая запись на диск проверяется оракулом** (fsck, ntfs-3g, перечитывание), как и раньше.
5. **Единый стиль.** Всё новое строим из `GlassKit` (панели, кнопки, плашки, шторки). После каждого экрана сверка скриншотом.
6. **Честность в README.** После каждой фазы обновляем таблицу «что есть / чего нет».

## A. Скорость USB (UAS)

**Что известно сейчас.** Работает USB Bulk-Only через публичный API Android (`UsbRequest`/`bulkTransfer`). Код UAS
(`UasExecutor`, `UsbUasTransport`) есть, но выключен (`ENABLE_UAS = false`). Публичный API режет каждую передачу примерно
до 16 КБ и не умеет «потоки» (bulk streams), которые UAS требует. Отсюда низкая скорость у SSD.

**Главное решение.** Основной выигрыш даёт не сам UAS, а переход на «сырой» usbfs. Java `UsbDeviceConnection.getFileDescriptor()` отдаёт
дескриптор, и через него из нативного кода (JNI) можно отправлять большие URB (сотни КБ) и держать несколько запросов в
полёте, а также вызывать `USBDEVFS_ALLOC_STREAMS`. Так работает libusb на Android. Поэтому два этапа, каждый можно
остановить, если не пойдёт:

- **A1. Замер.** Режим «Drive speed» в Settings уже есть. Записываем текущую скорость на вашем Crucial X8 (последовательное чтение 1 ГБ, случайное 4 КБ). Это базовая линия.
- **A2. Слой `libfeldusb.so` (C++, CMake, NDK 28 уже стоит).** Функции: взять fd, claim/set-interface, отправка и
  получение bulk-URB большого размера (256 КБ-1 МБ, глубина очереди 4-8, при `ENOMEM` уменьшаем), отмена, clear-halt, сброс.
  Kotlin-обёртка `UsbfsTransport` реализует существующий интерфейс `ScsiTransport`.
- **A3. Bulk-Only поверх usbfs.** CBW, данные большими кусками, CSW. Плюс кэш чтения с распознаванием последовательного
  доступа (8-32 МБ). Ожидание: многократный рост скорости при том же протоколе.
- **A4. UAS с потоками.** Распознавание интерфейса (класс 08, подкласс 06, протокол 62), разбор pipe-usage дескрипторов
  (команда, статус, данные), выделение потоков, Command IU / Sense IU / Read-Ready / Write-Ready. Тег команды = номер
  потока. Сначала только чтение; запись переводим на UAS позже, после проверки.
- **A5. Лестница отката:** UAS → Bulk-Only через usbfs → нынешний Java-путь. Автопереход при таймаутах и ошибках, список
  «плохих» устройств (как `unusual_uas.h` в Linux), переключатель «Режим совместимости» в Settings.
- **A6. Горячее отключение:** корректное завершение без падения; запись не оставляет полуфайл без пометки.

**Проверка.** Crucial X8 + любые другие носители, которые найдутся (флешка, кардридер). SHA-256 файла 4 ГБ читаем 3 раза
подряд, результаты равны. Отключаем шнур посреди чтения. Сравниваем с базовой линией A1.
**Готово, когда:** чтение X8 заметно быстрее базовой линии без ошибок данных; при любой неудаче автоматически работает старый путь.
**Риски:** SELinux или ядро производителя могут не пропускать ioctl потоков (тогда остаётся A3, это всё равно большой выигрыш);
капризные контроллеры. Сроки трудно оценить, пока не будет первого замера.

## B. DIT: хэши, копирование на два места, MHL

### B1. Хэши (`app.feldkit.hash`)
- **XXH64, XXH3-64, XXH3-128**: собственная реализация на Kotlin. Сверяем с `xxhsum` на длинах 0-300, на 1 МБ и на разных seed.
- **MD5, SHA-1, SHA-256, SHA-512** (JCA), **C4** (SHA-512 → base58 с префиксом `c4`), **CRC32** (уже есть).
- Один проход считает сразу несколько хэшей.
- Диалог «Checksum…» получает все алгоритмы. Результат совместим с `xxhsum`/`shasum` (проверим командами).
**Готово:** тесты с эталоном проходят, скорость на S21 не ниже ~500 МБ/с для XXH3 (иначе пересматриваем: вынести в JNI).

### B2. Движок offload (`OffloadJob`)
- Источник: выбранные файлы/папки или вся карта. Назначения: **одна или несколько папок через системный выбор (SAF)**:
  внутренняя память, SD-карта, любой накопитель, который Android сам смонтировал. Второй USB-накопитель без хаба технически невозможен.
- Каждый файл читается с источника **один раз**: хэш считается на лету, данные пишутся во все назначения параллельно
  (ограниченная очередь, без разбухания памяти).
- Затем **независимая проверка**: после `sync` читаем каждое назначение заново, считаем хэш и сравниваем с исходным.
- Журнал задания (JSON в приложении): после обрыва продолжаем с непроверенных файлов. Состояния файла:
  скопирован / проверен / не совпал / пропущен.
- Политика конфликтов (пропустить совпавшее, переименовать, спросить); пропуск уже скопированного по размеру и хэшу.
- Работает в `TransferService` (foreground), с паузой и отменой, удержанием экрана.
**Проверка.** Прогон на образах exFAT/APFS/NTFS и на настоящем X8. Вносим сбой (портим байт назначения) и проверяем, что
«не совпал» ловится. Хэш источника сверяем с `xxhsum` на Mac.

### B3. MHL
- **ASC MHL 2.0**: папка `ascmhl/`, файл поколения `NNNN_<папка>_<дата>.mhl` и `ascmhl_chain.xml` (хэш каждого .mhl),
  данные: путь, размер, время изменения, хэш (xxh64 по умолчанию, выбираем xxh3-128/md5/sha1/c4), сведения о создателе (FeldKit, версия,
  модель телефона), процесс «transfer».
- Простые файлы-сопровождения для тех, у кого нет MHL-программ: `.xxh64` / `.md5` / `.sha256`, совместимые с `xxhsum -c` / `shasum -c`.
- **Проверка по существующему манифесту**: выбрать MHL (или `.sha256`/`.md5`/`.xxh64`) и сверить с папкой. Это сильная
  самостоятельная функция.
**Проверка.** Эталон: официальный `ascmhl` (`pip install ascmhl`, **нужен интернет один раз**) и `xxhsum -c` на Mac. Если интернета не будет,
реализуем по спецификации и честно пишем в README «не проверено официальным инструментом».

### B4. Отчёт
PDF и CSV (системный `PdfDocument`): сводка задания, список файлов с хэшами, расхождения, скорости, модель накопителя, даты.
Кнопка «Поделиться».

### B5. Видео для съёмочных групп
- **Таймкод** (трек `tmcd` в MOV/MP4, MXF) и счётчик кадров поверх видео.
- **Покадровая перемотка**: Media3 `SeekParameters.EXACT` на шаг 1/fps; для VLC есть `nextFrame()`.
- **LUT**: загрузка `.cube`, применение на превью (`SingleColorLut` из Media3-эффектов).
- **Структура карт камер** (Sony XAVC, Canon, ARRI, RED `.RDC`, Blackmagic): показ клипа как набора файлов (`.XML`, `.THM`, `.LRV`), копирование клипа целиком.
- RED, BRAW, ARRIRAW **не берём** (нужны проприетарные SDK): показываем сведения и прокси, если есть. См. раздел «Что не делаем».

## C. Музыка

### C1. Тональность
- Хромаграмма (логарифмическая шкала по частоте, оценка настройки ±50 центов), профили мажора и минора, выбор модели
  обучением на ваших лупах (ground truth: тональность в имени файла, «Dmin», «F#m», «[a#m]»: те же `tools/make-*-real.py`).
- Вывод: «F# minor · 11A» (стандартная нотация и Camelot), доверие, и «относительный мажор/минор» как вторая трактовка.
- Для MIDI: точный подсчёт по нотам.
**Готово:** обучающая и проверочная выборки, честные проценты в README. Ожидание для лупов с гармонией 70-80 %. Ударные и шум дают «ключ не определён».

### C2. Форма волны
- Фоновое получение пиков (min/max на каждые 1024 сэмпла, несколько уровней детализации), кэш на файл. Декодер уже есть (`AudioPcm`).
- Отрисовка на `Canvas`: в строке плеера вместо тонкой линии, и крупная в карточке предпросмотра; тап и перетаскивание = перемотка.

### C3. A-B петля и скорость
- Метки A и B на волне (долгое нажатие / кнопки), включатель петли; на точку B вешаем сообщение плеера (`createMessage`),
  оно перебрасывает на A практически без паузы. Метки запоминаются для файла.
- Скорость 0.5-1.25 с сохранением высоты (`PlaybackParameters`) для разбора партий.
- **Прослушивание при перетаскивании**: короткие отрывки при движении пальца по волне.

### C4. Метаданные лупов и полевых записей
- WAV: `acid` (уже читаем), `smpl`, BWF `bext`, **iXML** (сцена/дубль/катушка/таймкод полевых рекордеров). Apple Loops (`basc` в AIFF/CAF: темп, доли, тональность), если такие найдутся в вашей библиотеке для проверки.
- Ableton `.asd` (рядом с лупом): пробуем разобрать темп и маркеры варпа. Формат недокументирован. Если за час не поддастся, откладываем.

### C5. Обзор проектов DAW
Показываем «что внутри» без запуска DAW: DAW и версия, темп, размер такта, число дорожек, список плагинов.
- **Ableton `.als`** (gzip-XML): полный разбор. **FL Studio `.flp`** (события: темп, название, версия). **REAPER `.rpp`** (текст). **Studio One `.song`** (zip с XML).
- **Logic `.logicx`, GarageBand `.band`**: это папки-пакеты. Показываем как проект с версией и готовым бонсом (bounce) внутри, глубокий разбор не делаем.
- **Pro Tools `.ptx`, Cubase `.cpr`**: закрытые форматы, только метка типа.

## D. Фото

### D1. XMP
- Лёгкий разбор XMP (`XmlPullParser`): встроенный пакет (JPEG APP1, TIFF, DNG, PSD) и **сайдкар `.xmp`** рядом с файлом.
- Поля: рейтинг, цветовая метка, заголовок, описание, ключевые слова, признак правки в Camera Raw (само наличие `crs:*`).

### D2. Режим отбора кадров
- Кнопка «Cull» в папке с фото: полноэкранный просмотр с жестами/кнопками: звёзды 1-5, «отклонить», «выбрать», цветные метки; прогресс «123/540»; фильтры (все, выбранные, без оценки, ≥3★, отклонённые).
- Сохранение: **сайдкары `.xmp` на диск**, если он доступен на запись (совместимо с Lightroom, Bridge, Capture One: `xmp:Rating`, `xmp:Label`);
  если диск только для чтения, оценки хранятся в приложении, а «Экспорт» отдаёт XMP/CSV.
- **«Скопировать только выбранные»**: фильтр → «выбрать всё в списке» → обычный поток копирования (+ сайдкары).
- Безопасность: существующий `.xmp` не пересобираем целиком, а правим точечно, сохраняя остальные узлы.
**Проверка.** Читаем записанные сайдкары другим инструментом (`exiftool`: `brew install exiftool`, **нужен интернет один раз**).

### D3. Гистограмма и GPS
- Гистограмма RGB и яркости (с предупреждением об обрезке теней и света) по уменьшенной копии кадра; включается в просмотрщике.
- Координаты и высота из EXIF, кнопка «Открыть в Картах» (`geo:`), экспорт GPX для папки. Встроенной карты нет, и сети приложение не просит.

### D4. RAW
- Сейчас показывается встроенное превью. Улучшаем выбор самого большого встроенного JPEG (SubIFD, `JpgFromRaw`, CR3/RAF/ORF/RW2/ARW/NEF/DNG) и честно пишем его разрешение в сведениях.
- **LibRaw (необязательно, решение за вами):** настоящее «проявление» RAW. +6-8 МБ к APK на архитектуру, лицензия LGPL/CDDL,
  24 МП около 3-6 секунд. Кнопка «Проявить (медленно)». См. вопросы.

## E. Дизайнеры и аниматоры

### E1. Превью проектных файлов
- **Универсальный экстрактор из Adobe XMP** (`xmpGImg:image`, base64-JPEG внутри): PSD/PSB (дополнительно к сведённой картинке), **AI, INDD, INDT**.
- **AI с PDF-совместимостью**: сначала пробуем `PdfRenderer`.
- Zip-контейнеры с готовым превью: **Sketch** (`previews/preview.png`), **Figma `.fig`**, **Adobe XD** (`preview.png`), **Krita `.kra`**,
  **OpenRaster `.ora`**, **Procreate `.procreate`** (`QuickLook/Thumbnail.png`). **Blender `.blend`**: превью и версия из заголовка (сжатые через gzip читаем, zstd пока нет).
- **Affinity, Clip Studio, Cinema 4D**: прямого превью там нет или формат закрыт. Покажем метку типа и размер; честно «превью недоступно».
**Проверка.** Нужны реальные файлы: PSD/AI/INDD/Sketch/Figma у вас на дисках есть? Если нет, соберём тестовые из открытых генераторов (скажите).

### E2. Шрифты и цвет
- **Шрифты TTF/OTF/TTC** (+WOFF): имя, начертание, версия, автор, лицензия (разбор таблицы `name`), редактируемый образец текста,
  сетка глифов, ползунок размера, оси вариативных шрифтов (`fvar`).
- **ICC-профили** из JPEG/PNG/TIFF/PSD: имя профиля и пространство (sRGB, Adobe RGB, Display P3, ProPhoto, CMYK), предупреждение о широком гамуте.

### E3. Покадровый просмотр и секвенции
- Покадровая перемотка и счётчик кадров/таймкод (общий код с B5), скорость 0.1-2×.
- **Секвенции изображений:** в папке находим пронумерованные ряды (`name.0001.ext`) и показываем как один клип; воспроизведение
  с выбором fps и буфером декодированных кадров. Форматы: PNG/JPG/TIFF (системный декодер), **TGA, DPX** (свой разбор),
  **EXR** (свой декодер: сначала ZIP/ZIPS/RLE, потом PIZ; многослойные файлы выбор слоя; тон-маппинг).
**Проверка.** Образцы генерирует `ffmpeg` (`-c:v dpx`, `-c:v exr` если сборка поддерживает, это проверим); для EXR сверяем значения пикселей с `ffmpeg` и (при интернете) `OpenEXR`.
- Видео с альфой (ProRes 4444, WebM VP9) на шахматном фоне.
- **Lottie** (`.json` по признакам схемы и `.lottie`): библиотека `lottie-compose` (Apache 2.0; **нужен интернет для скачивания**),
  ползунок кадров, сведения (fps, размер, длительность, слои).
- Проекты **After Effects `.aep`**: только метка типа и версия (формат закрыт).

## F. Разработчики

- **F1. Подсветка синтаксиса** (свой лёгкий токенизатор, без тяжёлых зависимостей): Kotlin/Java/C/C++/C#/JS/TS/Python/Go/Rust/Swift/Shell/SQL/JSON/YAML/TOML/XML/HTML/CSS/Markdown/INI/Dockerfile/Makefile; выбор по расширению и shebang; цвета в палитре приложения.
- **F2. Поиск внутри файла** (регистр, слово, регулярное выражение, «следующее/предыдущее», подсветка всех), переход к строке, перенос строк,
  масштаб текста щипком; режим больших файлов (постраничная подгрузка вместо нынешнего потолка 512 КБ).
- **F3. Редактирование (необязательно, см. вопросы):** только на доступном для записи диске и для текста ≤ 2 МБ; undo/redo; кодировка и
  окончания строк сохраняются; перед записью проверка, что файл не менялся; сохранение через временное имя. Проверяем fsck-циклом, как другие записи.
- **F4. JSON** (сворачиваемое дерево, копирование пути, поиск), **CSV/TSV** (таблица), **plist** XML и бинарный `bplist00` (для macOS-разработчиков).
- **F5. SQLite** (`.db/.sqlite/.sqlite3`, также Core Data): копия во временный файл, только чтение; список таблиц и схема, строки постранично, BLOB (картинки показываем), запросы `SELECT`, экспорт в CSV.
- **F6. Markdown**: показ «как отрисовано / исходник», заголовки, списки, таблицы GFM, блоки кода с подсветкой, относительные картинки с диска.
- **F7. Мелочи для разработчиков:** показ прав (mode/uid) в «Properties» там, где ФС их хранит; распознавание `.git` (ветка и remote из `HEAD`/`config`).

## Что я не буду делать (и почему)

- **RED / BRAW / ARRIRAW:** проприетарные SDK, в бесплатное приложение без аккаунтов их не включить. Покажем сведения и прокси.
- **Affinity, Cinema 4D, Pro Tools, Cubase:** закрытые форматы без стабильного превью. Метка типа и размер.
- **Редактирование медиа, монтаж, ретушь:** это другой продукт.
- **Облако, синхронизация, аккаунты:** противоречит принципу «ничего не покидает телефон».
- **Гарантия «на тысячу процентов»:** для любых определяемых величин (BPM, тональность) мы даём измеренную точность и честные проценты.

## Решения (зафиксировано после обсуждения)

1. **Порядок** принят, главное: пункты идут последовательно и не ломают друг друга (каждая фаза заканчивается зелёными тестами и рабочим приложением).
2. **Куда копировать:** пока достаточно системного выбора папки (SAF). Собственный выбор папки внутри приложения: позже.
3. **MHL:** решаю я: ASC MHL 2.0 + простые `.xxh64/.md5/.sha256`; хэш по умолчанию xxh64 (быстрее), xxh3-128 и md5/sha1/c4 выбираются.
4. **Редактирование текста на диске: делаем.** С подтверждением перед записью, проверкой после записи и откатом (undo/redo + «вернуть прежнюю версию»).
5. **LibRaw:** пока не берём (встроенные превью RAW), вернёмся, если понадобится: для музыканта и разработчика это не приоритет.
6. **Зависимости (Lottie и т. п.)** можно подтягивать, если они нужны.
7. **EXR/DPX-секвенции:** в самый конец фазы E (по усмотрению, это самая трудоёмкая часть).
8. **Тональность:** показываем обе нотации.
9. **Тест-материалы:** есть проекты Ableton (`.als`) и FL Studio (`.flp`) на X8. Остальные образцы ищем в свободном доступе или генерируем.
10. **Флешки и кардридеры для проверки USB:** позже, не сегодня.

Результат реального теста: на X8 тест скорости в Settings падал с сообщением «too small or could not be read». Диагностика добавлена
(`UsbBlockDeviceReader.speedReport`): тест теперь показывает скорость или точную причину для четырёх размеров команды.
